# Node provisioning: USB autoinstall, seven manual gestures, Ansible for the rest

ADR-0003 named this ticket in its own consequences: bare metal with Ansible
means the host does not install itself from a declarative API, so what it
actually costs to bring a machine from bare hardware to "Ansible can reach
it" had to be specified once #19 (storage layout) and #21 (orchestrator)
existed to specify it against. Both are in. #30's write-latency measurement
also destroyed this machine's existing installation (EFI, ZFS, swap) as a
side effect, so this isn't a hypothetical future node: it's the next real
action on this hardware, and the same procedure a later node would use.

A prior project iteration built a working `ansible/` tree for this exact
hardware (bare mirror at `homelab-gitlab-archive.git`): an autoinstall
`user-data`, and `base`/`zfs`/`tailscale`/`nvidia`/`nfs-client` roles. Read as
prior art, not doctrine, per the map's own standing rule: every fact below
that's re-derivable is re-derived, not copied; only the archive's
structural choices (locked-password bootstrap account, serial-based disk
disambiguation, ESP/ZFS mount-order fix) are reused, as reference, not as
files to adapt.

## Scope: homogeneous, node-1-first

This ADR assumes a future node looks like this one: same install
mechanism, same role set. The map's "Not yet specified" already carries "the
multi-node trajectory" (a heterogeneous node, no free NVMe slot to split,
possibly no GPU) as open fog; solving for unknown hardware now would be
exactly the premature specification wayfinder exists to avoid. That fog
stays fog until a second node is real.

## Install media: USB autoinstall, not PXE

PXE would remove the "carry a USB stick to the machine" gesture, at the cost
of a TFTP/DHCP-proxy service running permanently on a one-switch, no-VLAN
LAN for a gesture that happens a handful of times a year. Zero ongoing
infrastructure wins under the zero-budget, low-maintenance standing
constraints. USB it is, disambiguating the target disk via `storage.layout.
match.serial` matching udev `ID_SERIAL`, confirmed unchanged on Ubuntu
26.04 LTS (released 2026-04-23) against the archive's 24.04-era usage; the
one addition since Subiquity 24.08.1 is that `match` may now be an ordered
list of fallback specs, a strict superset of the single-serial form already
in use.

**Bootstrap account: `user-data.users`, not `identity`.** Subiquity's
`identity` section always provisions an active-password sudo user at
install time, and there is no documented knob to make it locked-password,
key-only. The archive's approach (a cloud-init `user-data.users` entry:
`lock_passwd: true`, `sudo: ALL=(ALL) NOPASSWD:ALL`, key auth only) is the
only documented route to that shape, confirmed still true today.

**Zero-touch: bake `autoinstall` onto the media's kernel cmdline.**
Subiquity's `Continue with autoinstall? (yes|no)` console prompt exists to
stop a stray config from wiping the wrong machine. That property is already
covered here independently: a `match.serial` disk action claims only the
one matched disk and fails the install outright if no matching disk is
present, on whatever machine the stick ends up in. Keeping the interactive
prompt on top would just reintroduce the "need a screen for this" cost
ADR-0003 exists to avoid, for a safety property already held elsewhere. The
media build patches the cmdline so install starts on insert + power, no
console required.

**Media build is scripted, not a manual procedure.** Stamping a stock ISO
with this node's `user-data`/`meta-data` (parametrized by serial, SSH
pubkey, hostname) and the cmdline patch is the same fixed sequence every
time; a script collapses several sub-gestures into one invocation, which
is what this ADR is trying to minimize. The script itself is not written by
this ADR: it belongs to building the platform, a separate effort per the
map's own destination.

## Addressing: static DHCP reservation, same as node 1

Node 1 already uses a router-side DHCP reservation, hardcoded as
`ansible_host` in `inventory.yml`. A new node's MAC isn't knowable until
after its first boot, so the reservation can't be pre-staged: boot once on
a dynamic lease, read the MAC, configure the reservation, and the IP that
lands in `inventory.yml` is now stable. Extending this to future nodes
reuses a pattern already proven working rather than adding mDNS to solve a
once-per-node inconvenience the router already solves in one click.

## k3s agent join: fetched live, nothing persisted

ADR-0007 already settled that a future node joins as a **worker**, never a
second server, one control plane forever. The join needs `K3S_URL` and
`K3S_TOKEN`; the token lives at `/var/lib/rancher/k3s/server/node-token` on
the primary, generated by k3s itself, not a value anyone chooses. The
Ansible role reads it live from the primary within the same play (a
delegated fact-gather) rather than persisting a copy anywhere. The primary
is always up (ADR-0005's 24/7 posture, ADR-0007's single-control-plane
finding), so there is always a live source of truth to ask, and persisting
a second copy of a secret that already has one would only add somewhere
else for it to leak or drift. ADR-0009's SOPS+age stays reserved for
secrets with no live source to query.

## Decision

**Manual gestures, "box arrives" → "Ansible can reach it" (6):**

1. Confirm the node's NVMe serial(s) via `udev ID_SERIAL`.
2. Generate a fresh SSH keypair dedicated to this node.
3. Run the (repo-versioned, written when the platform is built) media-build
   script with this node's serial, pubkey and hostname.
4. Write the resulting image to a USB stick, insert it into the target
   machine, power on. Nothing further.
5. Once it appears on the LAN, configure its DHCP reservation on the
   router.
6. Add the host to `ansible/inventory.yml`, a repo commit.

**Where Ansible takes over (gesture 7, the last manual one):**

7. `ansible-playbook ansible/site.yml -l <host>`, run from the repo root
   (the committed `ansible.cfg` there is what makes `-l` resolve against
   `ansible/inventory.yml` instead of silently targeting nothing).
   Everything else is unattended:
   base hardening (packages, SSH, chrony, unattended-upgrades, GRUB, the
   ESP/ZFS mount-order fix), ZFS state-pool creation with its ARC cap and
   `sanoid` snapshots, Tailscale enrollment, the NVIDIA driver, k3s agent
   join with a live-fetched token, NFS client mounts.

**Role set:** the archive's `base`, `zfs`, `tailscale` and `nfs-client`
roles are solid reference shapes for a fresh rewrite; so is `nvidia`. The
one real gap: the archive's `k3s` role was never actually written (an empty
`.gitkeep` stub); this project has to author it for real, with
server-mode (node 1) and agent-mode-plus-live-token-fetch (later nodes) as
genuinely new content, since ADR-0007's "one command to join" described the
CLI, not an Ansible role that doesn't yet exist.

## Alternatives rejected

**PXE network boot.** Removes the physical-USB gesture, but trades it for a
persistent TFTP/DHCP-proxy service on a flat, unmanaged-switch LAN: ongoing
infrastructure for a gesture that happens a few times a year. Rejected under
the zero-budget, low-maintenance standing constraints.

**Interactive autoinstall confirmation prompt, kept.** A second line of
defense against wiping the wrong machine, but redundant with the
`match.serial` gate that already holds that property, at the cost of
needing a screen on a headless-by-design box. Rejected.

**Persisting the k3s join token via SOPS+age.** Would match ADR-0009's
existing mechanism, but the primary node is always available to ask for a
value it already holds; persisting a copy adds a second thing that can
leak or go stale for no benefit over a live fetch.

**mDNS/`.local` addressing.** Solves the same once-per-node inconvenience
the router's reservation UI already solves, at the cost of a new dependency
on a network that isn't changing shape.

**Manual (unscripted) media build.** Considered simplest for something done
only a few times a year, but the same fixed sequence repeated by hand
invites the exact kind of slip a script exists to remove; scripting the
sequence is smaller than documenting it correctly every time.

## Consequences

- **A reinstall of the primary machine is the next real action this ADR
  unblocks**, not a hypothetical: #30 already forced it, and gestures 1-7
  above are the literal procedure for it, not just a future node's.
- **The k3s role is new work, not adapted work.** Nothing in the archive or
  in ADR-0007 already describes how an Ansible role fetches a live join
  token from a delegated host; that logic is authored when the platform is
  built, not specified further here.
- **The media-build script and every role are still unwritten.** This ADR
  settles their shape and inputs; writing them is building the platform, a
  separate effort per the map's own destination, and per the standing rule
  against configuration before the ADR it derives from is accepted.
- **The multi-node trajectory stays open fog**, deliberately: this ADR
  covers a node shaped like node 1. A heterogeneous node (no free NVMe slot
  to split, a different or absent GPU) is unspecified by construction and
  waits for that fog to resolve when it's real.
- **Zero-touch media is a one-way trust decision**: any USB stick built this
  way installs on whatever machine it's plugged into and matches its
  serial. Safe by construction against the wrong machine (the install
  simply fails), but the stick itself becomes something to handle like a
  credential, not a blank disk.
